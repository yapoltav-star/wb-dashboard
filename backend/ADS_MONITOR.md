# Контроль рекламных кампаний

`ads_monitor.py` проверяет кампании каждые 5 минут в единственном процессе Railway.
Создаёт разовую задачу Диле через Team CRM (`notify_now=true`); уведомлением Telegram занимается CRM.
Рекламные ставки, статусы и деньги монитор не изменяет.

Сигналы:
- наблюдавшаяся работающей кампания перешла из 9 в 7 или 11;
- подтверждённый нулевой остаток бюджета работающей/только что остановленной кампании;
- расходы за последние ~15 минут ≥500 ₽ и темп ≥3× среднего темпа предшествующих ≥30 минут.

Старые паузы при первом запуске не создают задачи. Ручную паузу WB не позволяет отличить
от аварийной только по статусу: задача просит проверить причину. Причина «бюджет исчерпан»
пишется только при полученном нулевом остатке. Сбои/пропуски API не считаются нулём.
Статистика WB запаздывает и может обновляться порциями, поэтому скачок — повод проверить,
а не доказательство перерасхода. На границе московских суток, при сбросе счётчиков или
разрыве наблюдений >30 минут обучение начинается заново.

Состояние и идентификаторы задач: Supabase settings `ads_monitor_v1`.
Сначала сохраняется инцидент, затем создаётся задача. При неопределённом результате POST
повторная попытка ищет маркер в CRM. Работа требует одного процесса/реплики (как scheduler
в основном приложении). Нельзя удалять журнал при работающем мониторе.
Для скачков новый инцидент допускается после ≥6 здоровых проверок и ≥6 часов от сигнала.

Настройки в settings `ads_monitor_config`: JSON
`{"enabled":true,"spend_ratio":3,"min_spend":500,"ignored_ids":[]}`.
`ignored_ids` — числовые ID кампаний с плановыми остановками/тестами.
Отключение: `enabled:false`. Статус и ошибки доставки: `/api/ads-monitor-status`.
Если CRM создала задачу, но Telegram не доставлен, задача не дублируется; ошибка видна
в `tasks[].notify_error`. Удалённые вручную задачи автоматически не пересоздаются.

Проверка: `python -m unittest discover -s backend -p 'test_ads_monitor.py'`.
